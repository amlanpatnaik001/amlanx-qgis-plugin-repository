## 1. What is AMLAN-X?

AMLAN-X is a static QGIS plugin catalogue. It gives users two ways to access published plugins:

- **Web catalogue:** search plugins by name or description, filter by category, view version information, and download the ZIP package.
- **QGIS Plugin Manager:** add the AMLAN-X XML feed to QGIS to find and install plugins and check for newer versions.

The catalogue is generated from versioned ZIP archives stored in the `plugins/` directory. GitHub Actions validates the archives, generates the catalogue files, and deploys the website to GitHub Pages.

**Publishing is performed through GitHub commits.** The public website is a static catalogue; it does not currently provide an upload form or authenticated administrator dashboard.

## 2. Install AMLAN-X in QGIS

Add the repository once in each QGIS user profile:

1. Open QGIS.
2. Select **Plugins → Manage and Install Plugins**.
3. Open the **Settings** tab.
4. Find **Plugin Repositories** and click **Add**.
5. Enter these values:

   **Name**

   `AMLAN-X QGIS Plugin Repository`

   **URL**

   `https://amlanpatnaik001.github.io/amlanx-qgis-plugin-repository/plugins.xml`

6. Ensure the repository is enabled and confirm.
7. Click **Reload all repositories** (or close and reopen Plugin Manager).
8. Open **All** or **Not installed**, then search for the plugin by name.
9. Select the plugin and click **Install Plugin**.

To receive a newer release, reload the repository and check the **Updates** tab.

### Troubleshooting: a plugin is missing from QGIS

Check these items in order:

1. Confirm the AMLAN-X repository is enabled in Plugin Manager settings.
2. Open the XML feed URL in a browser to confirm it is reachable.
3. Reload all plugin repositories.
4. Check the plugin's `qgisMinimumVersion` and `qgisMaximumVersion` fields in its `metadata.txt`. QGIS filters plugins according to their declared compatibility range.
5. Confirm the latest GitHub Actions workflow completed successfully in both **build** and **deploy** jobs.
6. Check that the ZIP filename and internal folder follow the rules in Section 4.

### Troubleshooting: QGIS says the plugin has “disappeared”

Use the versioned ZIP filename convention exactly. For example, plugin ID `fiberlink_address_autofill`, version `1.1.3`, should be packaged as:

`fiberlink_address_autofill.1.1.3.zip`

Avoid names such as `fiberlink_address_autofill-1.1.3.zip` or `fiberlink_address_autofill-1.1.3(1).zip`. QGIS may derive an incorrect plugin directory name from a hyphenated archive filename. Keep the plugin's internal folder name identical to its plugin ID.

## 3. Repository structure

The repository is organised as follows:

```text
amlanx-qgis-plugin-repository/
├── .github/
│   └── workflows/
│       └── publish.yml          # Validate, build, and deploy workflow
├── plugins/
│   ├── plugin_id/
│   │   ├── README.md            # Optional release notes / plugin guide
│   │   ├── plugin_id.1.0.0.zip  # Versioned plugin package
│   │   └── plugin_id.1.1.0.zip  # Later release
│   └── another_plugin_id/
│       └── another_plugin_id.1.0.0.zip
├── scripts/
│   └── build_repository.py      # ZIP validation and catalogue generator
├── site/
│   ├── plugins.xml              # Generated QGIS repository feed
│   └── catalog.json             # Generated website catalogue data
├── index.html                   # Public web catalogue
└── README.md                    # This guide
```

The files in `site/` are generated by the build script. Do not hand-edit generated output; update plugin ZIPs or the generator and allow GitHub Actions to rebuild the catalogue.

## 4. Add or publish a plugin

Create one folder under `plugins/` for each unique plugin ID. The GitHub folder name must exactly match the plugin's internal Python package / import folder.

### GitHub destination

Example for plugin ID `my_plugin` and version `1.0.0`:

```text
plugins/
└── my_plugin/
    └── my_plugin.1.0.0.zip
```

You may also keep a `README.md` in the GitHub plugin folder. It is for people browsing the source repository; the QGIS plugin itself is installed from the ZIP.

### ZIP structure

The ZIP must contain the plugin folder directly at its root:

```text
my_plugin.1.0.0.zip
└── my_plugin/
    ├── __init__.py
    ├── metadata.txt
    ├── my_plugin.py
    └── other_plugin_files...
```

**Correct:** `my_plugin/metadata.txt`  
**Incorrect:** `downloaded_folder/my_plugin/metadata.txt`  
**Incorrect:** `my_plugin/my_plugin/metadata.txt`

The build script looks for a root-level plugin folder containing `metadata.txt` and checks that its folder name matches the GitHub plugin ID directory.

### Required metadata

Each ZIP must contain a `metadata.txt` with a `[general]` section and these required fields:

```ini
[general]
name=My QGIS Plugin
qgisMinimumVersion=3.28
description=A concise description of the plugin.
version=1.0.0
```

Recommended additional fields:

```ini
author=Author Name
email=author@example.com
about=Detailed plugin description and usage notes.
homepage=https://example.com/plugin
tracker=https://github.com/owner/repository/issues
repository=https://github.com/owner/repository
category=Vector
experimental=False
deprecated=False
```

Use the actual minimum and maximum QGIS versions the plugin has been designed and tested against. Do not claim blanket compatibility with every QGIS or PyQt release. Plugins intended to run on Qt5 and Qt6 should use QGIS's `qgis.PyQt` abstraction and handle API differences where required.

### ZIP filename convention — important

Use this pattern:

`plugin_id.MAJOR.MINOR.PATCH.zip`

Examples:

- `fiberlink_address_autofill.1.1.2.zip`
- `fiberlink_address_autofill.1.1.3.zip`
- `batch_layer_exporter.1.0.1.zip`
- `slackloop_auto_naming.1.0.4.zip`

Keep the plugin ID unchanged between releases. Increase `version=` inside `metadata.txt` for every new release, and use the same version in the ZIP filename.

### Retain previous releases

Keep older valid ZIP archives in the same plugin folder if you want to preserve release history. The catalogue advertises the highest valid version for each plugin ID.

**Every ZIP found under `plugins/<plugin_id>/*.zip` is validated during a build.** A malformed, incorrectly structured, or metadata-invalid old archive can fail the entire build. Repair or remove invalid archives before publishing.

## 5. Publish using GitHub in a browser

Git and GitHub Desktop are not required. You can publish from the GitHub website:

1. Open this repository and go to `plugins/`.
2. Open the plugin's folder, or create it using **Add file → Create new file**. For example, create `plugin_id/README.md`.
3. Open the plugin folder.
4. Select **Add file → Upload files**.
5. Upload the versioned ZIP archive. **Do not extract the ZIP.**
6. Scroll down and click **Commit changes** to the `main` branch.
7. Open the **Actions** tab and select the latest **Validate and publish QGIS plugin repository** run.
8. Confirm both jobs — **build** and **deploy** — have green check marks.

A push to `main` automatically starts the workflow. You can also start it manually from the Actions tab using `workflow_dispatch`.

## 6. How automatic publishing works

The workflow in `.github/workflows/publish.yml` performs these steps:

1. Checks out the `main` branch.
2. Sets up Python 3.12 and installs the `packaging` dependency.
3. Runs `scripts/build_repository.py`.
4. Scans archives under `plugins/<plugin_id>/*.zip`.
5. Reads each archive's `metadata.txt` and validates the required fields, version, and matching plugin folder name.
6. Selects the highest version for each plugin ID.
7. Generates `site/plugins.xml` for QGIS Plugin Manager and `site/catalog.json` for the website.
8. Assembles the static website and deploys it to GitHub Pages.

If validation fails, the build stops. Review the error in the failed **build** job, correct the archive or metadata, and commit again. The previous successful Pages deployment remains the last published site until a new deployment succeeds.

## 7. Optional local validation

If Python is available, run these commands from the repository root.

Install the build dependency:

```powershell
py -3 -m pip install packaging
```

Build the catalogue:

```powershell
py -3 scripts/build_repository.py --root . --base-url "https://amlanpatnaik001.github.io/amlanx-qgis-plugin-repository"
```

The command creates or updates:

- `site/plugins.xml`
- `site/catalog.json`

Local validation is optional. GitHub Actions runs the same build during publishing.

## 8. QGIS and PyQt compatibility policy

Compatibility is declared separately by each plugin in its own `metadata.txt`:

- `qgisMinimumVersion` sets the lowest declared QGIS version.
- `qgisMaximumVersion`, when provided, sets the highest declared QGIS version.
- QGIS 3 installations may use Qt5 or Qt6 depending on the QGIS build.
- QGIS 4 uses Qt6.
- PyQt compatibility should be implemented through `qgis.PyQt` and version-aware API handling where required.

A successful ZIP validation or GitHub deployment does **not** prove that a plugin works at runtime. Test every plugin in the QGIS versions it declares, using copies of important projects and data before running operations that modify data.
